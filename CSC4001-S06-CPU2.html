Optimising the fetch-decode-execute-store cycle

Suppose the CPU can perform one stage per CPU cycle.

Von Neumann architecture is sequential

  • Suppose the computer can perform one stage per CPU cycle.

  • The ALU is only working during the Execute stage.

  • It would be ideal to have the ALU doing work all the time.

    We’ll look at three ways of getting the best use out of the hardware.

Pipelines

Overlap stages of the fetch-decode-execute-store cycle.

ALU receives a constant stream of work.

Instruction pipelining is a bit like a production line. Each piece of hardware has its designated job – Control unit for decoding, ALU for executing. Once an instruction is decoded, it is passed to the ALU for execution, while the ALU executes the instruction, the Control unit is decoding the next. This means the ALU is not sitting idle while the control unit decodes instructions for it.

Speedup

In a sequential fetch, decode, execute, store cycle, it takes 4 cycles for each instruction to complete.

  • 40 cycles for 10 instructions.

  • In a pipelined architecture:

    • It takes 4 cycles for the first instruction to exit the pipeline.
    • 5 cycles for the second
    • 6 for the third,
    • … and so on …
    • 14 for the 10-th instruction to exit the pipeline.

Speedup

\[ S_n = \dfrac{\text{Time to complete } n \text{ tasks sequentially}}{\text{Time to complete} n \text{ tasks in a pipeline}} \]

  • The speedup for 10 instructions in a 4 stage pipeline is \[ S_10 = \dfrac{40}{14} \approx 2.86 \]
  • The more instructions, the better! \[ S_{100} = \dfrac{400}{104} \approx 3.51, S_{1000} = \dfrac{1000}{1014} = 3.94 \]

For a pipeline with \(k\) stages, speedup approaches \(k\) as the number of instructions grows very large.

Mathematical explanation:

  • Suppose we have \(n\) instructions to complete.

    For a pipeline with \(k\) stages:

    • The first operation leaves the pipeline after \(k\) cycles.
    • The \(n\)-th instruction leaves the pipeline after \(k + n\) cycles.

    \(T_{\mathrm{pipeline}} = k + n\) CPU cycles.

  • Without pipelining, each stage is completed sequentially for each instruction.

    \(T_{\mathrm{seq}} = k \cdot n\) CPU cycles.

  • We can calculate speedup, a measure of how much quicker the pipelines system is: \[S = \dfrac{T_{\mathrm{seq}}}{T_{\mathrm{pipeline}}} = \dfrac{k \cdot n}{k + n}.\]

  • Pipelines work best for a large number of tasks: \(n \gg k\).

    Then \(S = k\).

Throughput and latency

  • Throughput: Number of instructions completed per unit time.

    • \(\text{Throughput} = \dfrac{\text{number of instructions}}{\text{execution time}}\)

    • Higher throughput indicates better performance.

  • Latency: time taken for a single instruction to complete (travel through the pipeline)

    • \(\text{Latency} = \dfrac{\text{execution time}}{\text{number of instructions}}\)

    • Lower latency indicates better performance.

Pipelines

Advantages

  • Higher throughput: more instructions per second
  • Better hardware utilisation: reduces idle time.
  • Well-suited to repetitive tasks.

Disadvantages

  • Higher latency: time taken to complete one instruction
  • More complex: increases design complexity, manufacture cost and, therefore, time.
  • Works most efficiently when kept full.

Pipeline hazards

  • Situations which cause the pipeline to stall, or have to restart.

  • Control dependency: which instructions should be pipelines after a jump?

  • Data hazards: when data dependence affecting instructions at different stages of the pipeline.

    • One instruction may depend on the result of a previous instruction still in the pipeline.
    • Read after write: one instruction attempts to read data which another instruction has not yet written.
    • Write after read: one instruction writes data after another instruction attempts to read it.
    • Write after write: one instruction attempts to write data after another, messing up register values.
  • control dependency: after a jump instruction, instructions may need to be loaded from a new location of memory. It is unknown, at the time the jump enters the pipeline, what its outcome will be, therefore the correct sequence of instructions cannot be pipelines.
    • Processors employ branch prediction to guess whether a jump is likely to happens or not. The “most likely” sequence of instructions are pipelined, meaning there is a high probability that the correct instructions are loaded into the pipeline. However, if branch prediction is incorrect, then the pipeline must be restarted, as different instructions need to be fetched, decoded, etc.
  • Data dependencies: one instruction may depend upon the result of another, so it must wait (stall) until its dependant has left the pipeline. Now we have a “bubble” (empty gap) in the pipeline.
    • There may be contention over registers wherein one instruction attempts to read or write to registers, or cache, being used by another. In this case, a calculation may have to be restarted, or at least the correct data loaded from memory (slowwww) again.

Reservation station and reorder buffer

Reservation station and reorder buffer

  • Some CPUs have multiple ALUs, or special-purpose hardware.

  • We want all of this hardware to be working all of the time.

  • However, we need to figure out which operations can be re-ordered or executed in parallel.

Example: Euclidean distance

  • Suppose we have two points, \(\mathbf{x}\) and \(\mathbf{y}\) in 2d space, e.g., in a 2d game.

  • To calculate the distance between \(\mathbf{x} = (x_1,x_2)\) and \(\mathbf{y} = (y_1,y_2)\), we use Pythagoras’ theorem.

    Euclidean distance, \(D = \sqrt{(x_2 - x_1)^2 + (y_2 - y_1)^2}\).

  • Let \(x_1 = 4, x_2 = 9, y_1 = 20, y_2 = 11\).

Don’t worry about the actual formula. It’s only important to note we have a square root, two multiplications, and an addition.

Sequential calculation

CPU can add, mul, sub and sqrt in a single CPU cycle.

  • t1 = x2 - x1
  • t2 = t1 * t1
  • t3 = y1 - y2
  • t4 = t3 * t3
  • `t5 = t2 + t4’
  • D = sqrt( t5 )

6 CPU cycles.

Note: sqrt is a relatively complex operation for computers and some CPUs do not include it as an instruction. However, many CISC (complex) architectures do.

Parallel calculation

Now suppose we have 2 ALUs.

  • t1 and t3 can be computed
  • Given t1 and t3, t2 and t4 respectively can be computed in parallel.
  • t5 must wait for t2 and t4,
  • The result, D depends on t5.

… but how can the CPU, a clump of transistors, figure this out?

The key is to make a table of instructions, and use a status flag to determine dependencies.

Table of instructions

# Instruction Arg 1 Arg 2 Return Status
1 SUB x2 x1 t1 Waiting
2 MUL t1 t1 t2 Waiting
3 SUB y2 y1 t3 Waiting
4 MUL t3 t3 t4 Waiting
5 ADD t2 t4 t5 Waiting
6 SQRT t5 – D Waiting

We know the value of x1, x2, y1 and y2: fill them in.

We start by writing our instructions in a table. CPU does this as they come out of the decode stage of the pipeline (very fast) We need to know the inputs (Arg1 and Arg2) and return values to figure out dependencies. First step: fill in any variables whose values we know already.

step 4: finally, t6, depending on t5, is ready.

We were able to parallel some, but not all, of the instructions. Executing 6 in 4 steps. giving a speed up of 6/4 = 1.5. Parallel computing is a whole module. no a whole degree, and multiple PhD’s, and it takes clever programming to get the best speedup while maintaining proper synchronisation.
