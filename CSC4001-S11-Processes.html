Processes

CSC4001: Computer Systems and Architecture

Learning Outcomes

  • Define a process in the context of operating systems, stating the information the operating system needs to manage a process.
  • Summarise the basic states in the process lifecycle and draw a diagram illustrating the state transitions the OS can make.
  • Explain how a computer is booted.

Recap: operating systems

Early computers such as EDSAC had no operating system.

  • Programmers had to write their programs for the hardware,

  • Lots of low-level, repeated code,

  • programs manually loaded by an operator.

Recap: operating systems

  • Later, a program called the Monitor was introduced.

  • Allowed scheduling of multiple programs.

  • All programs had equal access:

    possible for one program to overwrite another, even the monitor.

  • Co-operative multitasking:

    a program had to surrender control back to the monitor.

  • Meant erroneous or malicious programs could crash the whole system.

Recap: operating systems

  • Hardware support was later added to protect resources:

    • Instruction levels:

      only the Monitor could run privileged instructions.

    • Memory management unit:

      kept track of which areas of memory each process could read, write or execute.

Recap: operating systems

  • Device drivers to interface with hardware were written,

  • along with code libraries for common operations.

  • Linkers and loaders build to allow programs to access external code,

    enabling code re-use.

Recap: operating systems

  • A program responsible for

    • Managing and protecting resources

      e.g., CPU, memory, disk, network.

      • prevents accidental or malicious damage,
      • provides efficient use of limited resources.

    • Providing a programming interface:

      • written by experts to get best performance out of hardware,
      • less chance of errors as experts understand the pitfalls,
      • prevents repeating low-level code.

Recap: operating systems

Desirable attributes:

  • Lightweight and efficient

    so that as many resources as possible can be dedicated to user-land applications.

  • Flexible and easy to use,

    i.e., it should be a help, not a hindrance, to the programmer.

A good operating system is the one you do not notice is there.

Processes

Process

Collection of data held by the operating system:

  • Code (machine instructions),

  • Data,

  • Metadata required by the operating system.

  • Also known as

    task, job.

  • Not to be confused with

    processor, program.

Process vs program

  • A program may consist of several processes.

  • E.g., one process builds an image, a different process renders it.

  • Another design pattern enabling separation of concerns,

    called structure by process.

  • Less common in modern computers, which use threads,

    although one process is still used for each browser tab, to provide security.

Process metadata

OS requires some information in order to run a process:

  • where in memory to find the code and data,
  • memory permissions (i.e., the MMU flags),
  • allocation (how much CPU time, memory, I/O it is allocated),
  • usage statistics (how many CPU cycles, how much time),
  • saved CPU state (e.g., contents of registers).

This allows the OS to manage and protect resources.

Process states

  • OS keeps track of the state of each process – basic states are

    • New: a process which has just been created,

      OS needs to do some setup,

    • Running: currently being executed on the CPU,

    • Ready: waiting to be scheduled, can be run immediately,

    • blocked: cannot be run because it is waiting for something,

      e.g., data to be read from disk,

    • Exit: process has finished,

      OS needs to clean up.

Scheduling

Deciding which process should run next.

  • I.e., OS moves processes from one state to another.

Process lifecycle

  • Typically, one process requests creation of another,

    called forking or spawning.

    • E.g., user clicks the web browser icon on their desktop.

    • Desktop GUI program makes a syscall to the OS,

      requesting creation of a new process, running the web browser program.

    • If allowed, OS creates the new process.

      Syscall returns an exit code indicating success or reason for failure.

      • E.g., no permission to create processes,
      • Insufficient resources – too many processes running already.

Process lifecycle

  • All processes start in the new state.

    metadata needed to run the process is called the process control block (PCB).

    • OS initialises process PCB datastructures,
    • allocates memory,
    • allocates a process ID (unique identifier for each process),
    • sets initial priority importance, used by the scheduler),
    • adds the process to the scheduler’s list,
    • then moves process to the ready state.

  • From the ready state,

    process can be moved to running when the OS decides to schedule it.

Process lifecycle

Process lifecycle

  • When the OS decides to schedule a process, it is dispatched.

  • Jump and drop CPU instruction is performed,

    • Jump to the memory location containing process instructions,
    • Drop from privileged (only allowed by the OS) mode to unprivileged mode.

  • A process may voluntarily surrender control,

    i.e., relinquish,

    • save state (of CPU registers, MMU etc),
    • process moved to ready.

  • Same happens if the process is interrupted, or its timeslice is over.

Process lifecycle

  • If the process requires I/O, e.g., read from / write to disk,

    it makes a syscall, asking the OS to perform the operation.

    • state saved, process moved to blocked,

  • When the operation is complete,

    • process moved to ready,
    • will not be running until the OS schedules it.

Process lifecycle

  • Every process finishes in the exit state.

    OS does some cleanup

    • deallocating memory,
    • releasing resources (e.g., closing files),
    • deallocating the process control block.
    • remove the process from the scheduler’s list.

Process hierarchy

  • A basic list is not an efficient datastructure for the scheduler.

    other representations are preferred, e.g.,

    • priority queue
    • process tree.

Process hierarchy

  • Unix uses a process tree,

    • first process created, called init is the root of the tree.

    • new processes become the children of the process which requested their creation,

    • allows processes to be grouped,

    • Each group of processes has a process leader.

    • Processes can be treated as a group,

      E.g., killing the process leader causes all processes in its group to be killed, too.

Bootstrapping

How to get started?

“Pull yourself up by your bootstraps!”

Booting a computer

  • Process of starting the OS.

  • Complicated process: needs to identify and set up hardware, load and initialise the OS, start the initial process.

    Only then can user-land programs be started.

Booting a computer

  • Each computer has a small amount of non volatile memory,

    flash memory whose data remains saved when there is no power.

  • On startup, CPU is configured to jump to this memory and begin running instructions.

  • Tiny program called the bootstrap loader, to load a larger program from other memory

  • Several rounds of bootstrapping may be needed until we have a program large enough to read from disk.

Bootloader

  • Program loaded after initial bootstrapping,

  • Contains instructions to start the OS

    • may ask the user to choose which OS to start,
    • knows how to start the OS, and
    • where to find it, e.g., hard disk or network.

  • On Linux, e.g., raspberry pi, boot instructions can be found in

    etc/init.d/
